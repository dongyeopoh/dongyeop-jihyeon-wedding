# 0004. 배포는 현재 빌드만 담은 스냅샷 커밋을 gh-pages 에 올리는 방식, dist 는 main 에서 제외

## 배경

2026-10-26 에 계좌번호를 소스에서 지웠지만, 그때까지의 배포 방식(`dist/` 를 main 에 커밋하고 `git subtree push` 로 gh-pages 에 복제)은 main 의 옛 빌드 커밋 13개를 gh-pages 에 그대로 옮겨 놓고 있었다. 계좌번호가 든 옛 번들이 두 브랜치의 이력에 영구히 남고, 이력을 지워도 다음 subtree push 가 다시 복제한다. 또 `dist/` 가 main 에 있으면 빌드마다 옛 번들이 이력에 쌓인다.

## 결정

- `dist/` 는 `.gitignore` 대상이며 main 에는 소스와 문서만 둔다.
- 배포는 `npm run deploy`(`scripts/deploy.sh`) 한 명령으로 한다: 커밋되지 않은 변경이 있거나 main 이 아니면 거부 → 린트 → 빌드 → 미리보기를 띄워 사람이 휴대폰 너비로 확인하고 `y` → 현재 `dist/` 내용만 담은 커밋을 직전 gh-pages 커밋의 자식으로 만들어 보통 푸시. 강제 푸시는 쓰지 않는다.
- main 과 gh-pages 의 옛 이력은 2026-10-26 에 한 번 새로 시작했다(각각 커밋 하나에서 출발).

## 검토한 대안

- **subtree push 유지, 이력만 한 번 정리**: 다음 배포 때 옛 커밋이 다시 복제되어 정리가 무효가 된다. 기각.
- **GitHub Actions 로 자동 빌드·배포**: 사람의 화면 확인 단계가 사라지고, 지도 키를 저장소 비밀로 옮겨야 하며, 1년에 몇 번 없는 배포를 위해 워크플로를 유지해야 한다. 기각.
- **`gh-pages` npm 패키지**: 스냅샷 방식과 결과가 같지만 의존성이 하나 늘고 거부 조건·확인 질문을 넣을 수 없다. 기각.

## 결과

- 배포 때마다 사람이 미리보기를 보고 `y` 를 눌러야 한다. 무인 배포는 불가능하다.
- gh-pages 이력은 배포 회차만큼만 쌓이고, 각 커밋은 그 시점의 사이트 전체다. main 이력에는 번들이 없다.
- 다른 컴퓨터에서 먼저 배포하면 푸시가 거부되고, 다시 실행하면 새 부모 위에 만들어진다. 2026-10-26 이전에 받아 둔 클론은 새로 받아야 한다.
- 결정 0001 의 "main 에 dist 커밋, subtree push" 부분은 폐기되었다. "저장소 하나, 자동화 없음" 은 유지된다.
