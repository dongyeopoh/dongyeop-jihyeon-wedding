# 0001. 한 저장소에서 main 은 소스+빌드, gh-pages 는 배포 전용, 자동화 없이 subtree push

> **2026-10-27 에 0004 로 대체되었다.** subtree push 는 main 의 옛 빌드 커밋을 gh-pages 에 그대로 복제해, 삭제한 개인정보가 든 옛 번들이 영구히 남는 문제가 있었다. 아래는 당시 결정의 기록이다. 지금 유효한 것은 "저장소 하나, 배포 자동화 없음" 뿐이다.

## 배경

GitHub Pages 로 청첩장을 공개해야 했다. 처음에는 "소스를 관리하는 저장소" 와 "Pages 로 공개하는 저장소" 가 달라야 한다고 이해해서 공개 저장소의 main 에는 빌드 결과(`dist/`)만 올리고 소스는 로컬에만 두었다. 2026-10-20 에 Pages 는 같은 저장소의 gh-pages 브랜치만 읽으므로 main 에 소스를 올려도 공개에 영향이 없다는 것을 확인했고, 소스가 한 컴퓨터에만 있는 상태의 위험(분실 시 복구 불가)을 없애기로 했다.

## 결정

- 저장소는 `dongyeopoh/dongyeop-jihyeon-wedding` 하나다.
- `main` 에 소스, 문서, 그리고 빌드 산출물 `dist/` 를 함께 커밋한다.
- `gh-pages` 는 `git subtree push --prefix dist origin gh-pages` 로만 갱신하며 손으로 건드리지 않는다.
- 빌드·배포 자동화(GitHub Actions 등)는 두지 않는다. 배포는 사람이 로컬에서 빌드하고 눈으로 확인한 뒤 올린다.

## 검토한 대안

- **GitHub Actions 로 main 푸시 시 자동 빌드·배포**: `dist/` 를 커밋할 필요가 없어지고 `-f` 함정도 사라진다. 그러나 네이버 지도 키를 저장소 secret 으로 옮겨야 하고, 1년에 몇 번 있을까 말까 한 수정을 위해 워크플로를 유지·디버깅하는 비용이 더 크다고 보았다. 보존 모드인 프로젝트에 맞지 않아 보류.
- **소스 전용 비공개 저장소를 따로 두기**: 원래 의도였으나 저장소가 둘이면 어느 쪽이 최신인지 추적해야 하고, 방명록 이슈가 공개 저장소에 묶여 있어 결국 공개 저장소를 없앨 수 없다. 이점이 없어 기각.
- **`gh-pages` npm 패키지로 배포**: subtree 와 결과가 같고 의존성만 하나 는다. 기각.

## 결과

- 소스 변경 커밋에는 항상 새 `dist/` 가 포함되어야 하며, 그렇지 않으면 배포와 소스가 어긋난다.
- `.gitignore` 의 `dist` 줄과 추적 중인 `dist/` 가 충돌하는 상태가 생겼고, 해소(줄 삭제) 전까지는 `git add -f` 가 필요하다.
- 다른 컴퓨터에서도 `.env` 만 만들면 같은 결과를 빌드할 수 있다. 빌드 자동화가 없으므로 "누가 언제 배포했나" 는 커밋 기록으로만 남는다.
